## Attribution limits and next counters

In the checked-in probe header, FreeTree node writes are bucketed only as allocation body, refill, reserve return, post-publish reclaim, or other (`perf_probe.h:70-95,130-136`; `btree.c:210-229`). Allocation, refill, reserve return, and post-publish reclaim have phase scopes at the call sites above. Direct `bfs_freespace_free` writes (including interface-retirement fallback), `bfs_freespace_add` (`alloc.c:344-420`), and sealed replacement are not separately identifiable in `OTHER`. Allocation-body writes also do not distinguish public data allocation from metadata-interface fallback, or distinguish the allocator's mutation shapes. `iface_alloc_calls`/`iface_free` CPU accounting does not identify spare-versus-FreeTree outcomes (`alloc.c:251-263,297-309`). Reserve batch counts combine root fold with root-leaf batch. The reported create/write/delete totals do not establish which `alloc.c` path accounts for FreeTree writes.

The frozen ABI 13 instrumentation source is available in `build/split-coalesce-attribution-source`. `perf_paths.h:8-33` classifies tree roles and increments split/coalesce matrices by root/deep shape and event; `perf_probe.h:34-44,153-156` defines the dimensions. Split attempts and leaf/internal right-read/right-write sites are instrumented in `btree.c:898-932,963-991`, with the initial split writes at `750-754,797-802`. Thus the reported directory right-read/right-write events map to explicit leaf-split hooks, and zero internal-split attempt cells mean those diagnostic workloads did not enter the internal-split path. The two-sided and right-only free-merge branches record attempts immediately before their edits and completion only after success (`alloc.c:845-895`). The reported zero attempt counts for both kinds across all roles and heights therefore establish no such branch hits in those workloads; these branches do not need priority remeasurement. This is direct hook evidence, separate from inference from aggregate writes. These hooks are diagnostic additions at the same algorithms and branch sites as the normal source reviewed above.

Highest-information next counters, if instrumentation is authorized:

1. Split allocation-body requests by origin (public data/extent versus metadata-interface fallback) and operation shape: single-block tail update/delete, multi-block exact-fit delete, non-root-leaf partial delete+insert, root-leaf replacement, and errors/rollback. Record request count, requested/result blocks, tree height, FreeTree node reads/writes, and elapsed allocator-body time per class. This is the largest currently undifferentiated phase and ties operation traffic to actual request types.
2. Split `OTHER` node writes by producer: direct range free, metadata-interface-free fallback, `bfs_freespace_add`/format, sealed replacement, and other cleanup. Keep zero-write attempts and writes distinct; this exposes CPU/search work as well as node writes. The two-edit free-merge attempts are already zero in the reported matrix.
3. Count metadata-interface allocation outcomes (`recursive reserve`, emergency, spare, public-allocation fallback) and retirement outcomes (`recursive reserve`, metadata spare, ordinary free, deferred older block). Keep requests separate from writes; successful spare reuse is a CPU path with zero FreeTree writes.
4. Split reserve-return batch attribution into owned-root fold versus private root-leaf batch, and count attempted/applied/fallback results. Existing run, batch, and skip counters already supply most remaining shape/block/write evidence (`perf_probe.h:75-94`). For sealed commit, count applied blocks and replacement node writes; `sealed_commits` and `sealed_metadata_fences` report success milestones only (`txn.c:233-260`).

Search/edit counts above are source-derived upper-path observations, not runtime hit counts. No optimization or instrumentation was changed in this review.
